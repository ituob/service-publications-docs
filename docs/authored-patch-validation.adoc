= Authored patch validation

== Design and boundary

Approval commits authoritative patch bytes to
`ituob/itu-ob-data:ob-issues/{issue}/{slug}/NNN-ACTION.yaml`.
The reusable service workflow validates an explicit data head SHA against an
explicit base SHA. It checks out trusted service code at a separate explicit
service SHA matching the caller's pinned reusable workflow reference; it never
uses the data repository's `github.sha` to select executable service code.

The staging gate reads blobs from the exact head commit, checks the checkout
matches that commit, rejects symlinks, unsafe paths and generated-state writes,
and overlays the cumulative authored head byte for byte onto the existing service
corpus. The exact base-to-head diff governs append-only policy; the manifest
records changed paths separately from all staged paths. This preserves earlier
data PRs even when their patches are absent from the legacy service baseline.
Existing different bytes at the same historical path fail with that path.
Identical historical copies are accepted to permit a later canonical migration;
they do not change the effective corpus. Identical bytes are not an exemption
from incoming model and replay gates: legacy naming or shape defects still
fail and must be resolved before those records can be canonically copied.
Modifications, deletions and renames of
already authored patches fail until an approved unpublished-withdrawal metadata
contract exists. No publication status is inferred from invented fields.

The gate records SHA-256 digests for every incoming patch and verifies both the
head checkout and staged corpus after the full validation pipeline. It never
runs `build_ob_issues.rb` over authored patches. Trusted legacy corpus files and
seed datasets remain in the service repository at this baseline. This overlay is
a validation boundary, not completion of the pending full SSOT migration.

Each incoming patch must resolve to a replayable catalog register and its
modeled amendment class. Its envelope and item payload are validated directly
from the submitted bytes. Existing full corpus LML, dataset and reference gates
remain required. Derived changes are regenerated from the combined corpus;
snapshots are rebuilt and checked for integrity, and incoming additions must
appear in the derived changes and replay history. Parser equivalence runs when
the legacy source tree is unchanged, without recapturing any baseline.

New issues require `ob-issues/{issue}/meta.yaml`, either in the trusted corpus or
added in the same data PR. Submitted metadata is preserved and hashed like patch
bytes, validates through `IssueMetadata`, and must carry a matching issue id and
valid publication and cutoff dates. Missing metadata fails with a prerequisite
message. The gate does not synthesize metadata or weaken model validation. Real D1
publication is outside this workflow; snapshots provide local replay evidence.

== Caller contract

The caller pins `uses: ituob/service-publications-docs/.github/workflows/validate-itu-ob-data.yml@<service SHA>`
and passes that same 40-character commit SHA as `service_ref`, the data PR head
SHA as `data_ref`, and the PR base SHA as `base_ref`. `data_repository` defaults
to, and is restricted to, `ituob/itu-ob-data`. No repository secrets are required.
The job has read-only repository permissions and never executes data checkout
scripts or workflow files.

== Authoring format and policy

The accepted action filenames are exactly `NNN-ADD.yaml`, `NNN-SUP.yaml`,
`NNN-REP.yaml`, `NNN-LIR.yaml`, `NNN-MOD.yaml`, `NNN-DEL.yaml`, and
`NNN-SEED.yaml`, under a registered, replayable amendment slug. The envelope
`type` must match the filename, `ob_issue_no` must match the directory, and
`identifier.code` must be a nonempty string. `data._class` must name the slug's
amendment model; nested actions and entries validate through that model's
attribute classes. Unknown modeled keys and serialized class substitutions fail.
Full-state objects or arbitrary model serializations are not patch authoring.

Legacy `issues/` sources and inert `docs/`, workflow YAML, README, LICENSE and
`.gitignore` maintenance may accompany a data PR. Unknown top-level paths and
`datasets/`, snapshot or generated-state writes fail. All data Git entries must
be regular files; authored YAML must not be executable. Neither data scripts nor
its workflow files are executed by this service workflow.

The service bundle uses `BUNDLE_GEMFILE=ituob/Gemfile`. Gate order is direct
incoming model validation, changes migration, full LML validation, dataset
validation, references, applicable parser equivalence, snapshot generation and
integrity, incoming replay witness, then exact-byte recheck. The final recheck
runs even after a failed gate. `authored-patch-proof` retains the digest manifest
and generated snapshots in hosted CI. No source or baseline normalization is
performed and no parser baseline is recaptured.

== Focused verification

Run the Git/byte boundary regressions with the Python standard library:

[source,sh]
----
python3 -m unittest discover -s scripts/tests -q
----

With Ruby 3.4 and the trusted service bundle installed, enable the tests which
execute the actual workflow model and replay gates (including hostile nested
keys, class substitution and a history-only ADD without an active snapshot row):

[source,sh]
----
AUTHORED_PATCH_RUBY_TESTS=1 BUNDLE_GEMFILE=ituob/Gemfile \
  python3 -m unittest discover -s scripts/tests -q
----

The workflow deliberately fails closed when an otherwise modeled action cannot
be projected and replayed by the current adapters. In particular, declaring a
SEED action alone does not prove a seed batch was replayed: its authored entry
keys must appear in the issue snapshot. Supporting a new action representation
requires the migration/replay adapter to produce that evidence as well.
